## 2. Функция 1: Аутентификация

### Что делает

Supabase Auth создаёт **анонимную сессию** для идентификации устройства/сессии пользователя.

### Где используется

**Файл:** `lib/modules/vms/core/auth_controller.dart`

```dart
// Строка 79-80
await Supabase.instance.client.auth.signInAnonymously();
final uuid = Supabase.instance.client.auth.currentUser!.id;
```

### Зачем нужно

1. Получение уникального `UUID` для сессии
2. Привязка сессии к устройству
3. JWT токен для авторизации запросов к Edge Functions

### Поток данных

```
1. Пользователь вводит NEAR credentials
            │
            ▼
2. signInAnonymously() → Supabase создаёт анон. юзера
            │
            ▼
3. Получаем UUID (Supabase user ID)
            │
            ▼
4. UUID используется для связи Session ↔ User
```

### Варианты замены

| Вариант | Описание | Сложность |
|---------|----------|-----------|
| **UUID на клиенте** | Генерировать UUID локально через `uuid` package | Простая |
| **Device ID** | Использовать идентификатор устройства | Простая |
| **NEAR Account ID** | Использовать accountId как идентификатор сессии | Простая |
| **Подпись сообщения** | Каждый запрос подписывать NEAR ключом | Средняя |

### Рекомендация

**Использовать NEAR Account ID как идентификатор сессии.** Это естественный выбор для децентрализованного приложения — аккаунт блокчейна уже является уникальным идентификатором.

```dart
// Вместо:
await Supabase.instance.client.auth.signInAnonymously();
final uuid = Supabase.instance.client.auth.currentUser!.id;

// Использовать:
final sessionId = accountId; // e.g., "user.near"
```

## 3. Функция 2: Верификация NEAR аккаунта

### Что делает

Edge Function `verifyAccount` проверяет, что пользователь действительно владеет NEAR аккаунтом, верифицируя криптографическую подпись.

### Где используется

**Файл:** `lib/modules/vms/core/auth_controller.dart`

```dart
// Строки 161-174
final response = await Supabase.instance.client.functions.invoke(
  'verifyAccount',
  body: {
    'signature': signature,
    'publicKeyStr': publicKeyStr,
    'encryptionPublicKey': encryptionPublicKey,
    'uuid': uuid,
    'accountId': accountId,
  },
);
```

**Файл:** `supabase/functions/verifyAccount/index.ts`

```typescript
// Строки 21-38 — верификация подписи
async function verifySignature(signature, publicKeyStr) {
  const signatureBytes = bs58.decode(signature);
  const publicKey = nearApi.utils.PublicKey.from(publicKeyStr);
  const isVerified = publicKey.verify(new Uint8Array([]), signatureBytes);
  return isVerified;
}
```

### Зачем нужно

1. **Доказательство владения аккаунтом** — без приватного ключа нельзя создать валидную подпись
2. **Защита от спуфинга** — нельзя притвориться другим пользователем
3. **Создание/обновление User** — сохранение encryption public key

### Поток данных

```
1. Клиент подписывает сообщение приватным ключом NEAR
            │
            ▼
2. Подпись + публичный ключ → Edge Function
            │
            ▼
3. Edge Function верифицирует подпись через near-api-js
            │
            ▼
4. Если валидно → создаёт/обновляет User в БД
            │
            ▼
5. Создаёт/обновляет Session
```

### Варианты замены

| Вариант | Описание | Сложность |
|---------|----------|-----------|
| **Клиентская верификация** | Верифицировать подпись на клиенте | Простая |
| **Без верификации** | Доверять введённым данным (небезопасно) | - |
| **Smart Contract** | Верификация через контракт NEAR | Высокая |
| **Публичный сервис** | Использовать существующий NEAR indexer API | Средняя |

### Рекомендация

**Клиентская верификация.** Библиотека `near-api-js` (или её Dart аналог) может верифицировать подписи локально. Для децентрализации это идеальный вариант.

```dart
// Верификация на клиенте
import 'package:flutterchain/...';

bool verifySignature(String signature, String publicKey, String message) {
  // Использовать crypto библиотеки для верификации ed25519
  return nearBlockChainService.verifySignature(signature, publicKey, message);
}
```

**Важно:** Текущая реализация верификации на сервере нужна, чтобы **доверенная сторона** подтвердила владение аккаунтом. При децентрализации эта роль переходит к самому блокчейну или к другим участникам сети.

## 4. Функция 3: Хранение ключей шифрования

### Что делает

Supabase хранит **публичные ключи шифрования** пользователей для E2E encryption сообщений.

### Где используется

**Сохранение ключа** — `verifyAccount` Edge Function:

```typescript
// Строки 95-101
const [updatedUser] = await db
  .update(user)
  .set({
    updatedAt: new Date(),
    publickey: encryptionPublicKey,  // ← Сохраняем публичный ключ
  })
  .where(eq(user.id, existingUser.id));
```

**Получение ключей** — `chat_page.dart`:

```dart
// Строки 131-135
final data = Supabase.instance.client.from('User').select();
for (final id in participants) {
  data.eq('id', id);
}
final accounts = await data;

// Строка 138
final accountPublicKeyForEncryption = accounts[i]['public_key'];
```

### Зачем нужно

1. **E2E шифрование** — сообщения шифруются публичным ключом получателя
2. **Приватность** — только получатель может расшифровать своё сообщение
3. **Обмен ключами** — пользователи должны знать публичные ключи друг друга

### Поток данных

```
ОТПРАВКА СООБЩЕНИЯ:

1. Отправитель получает public_key получателя из БД
            │
            ▼
2. Шифрует сообщение этим ключом
            │
            ▼
3. Отправляет зашифрованное сообщение

ПОЛУЧЕНИЕ СООБЩЕНИЯ:

1. Получатель загружает зашифрованное сообщение
            │
            ▼
2. Расшифровывает своим приватным ключом (из SecureStorage)
```

### Варианты замены

| Вариант | Описание | Сложность |
|---------|----------|-----------|
| **NEAR Social DB** | Хранить public_key в SocialDB контракте | Средняя |
| **Обмен при создании чата** | Передавать ключи при первом сообщении | Средняя |
| **IPFS + индексер** | Хранить в IPFS, индексировать | Высокая |
| **Локальный кэш** | Сохранять ключи собеседников локально | Простая |

### Рекомендация

**NEAR Social DB.** Уже используется в приложении для профилей. Можно добавить поле `encryption_public_key` в профиль пользователя.

```javascript
// Структура в SocialDB
{
  "user.near": {
    "profile": {
      "name": "User Name",
      "encryption_public_key": "ed25519:ABC123..."  // ← Новое поле
    }
  }
}
```

## 5. Функция 4: Система чатов

### Что делает

Supabase хранит **чаты и сообщения** в PostgreSQL и предоставляет API для CRUD операций.

### Компоненты

#### 5.1 Создание чата

**Клиент:** `user_chats_page_controller.dart`

```dart
// Строки 55-62
final response = await Supabase.instance.client.functions.invoke(
  'chat_creation',
  body: {
    'id': chatId,          // SHA256 hash участников
    'metadata': {
      'chat_type': 'private',
      'participants': [currentUserId, otherUserId],
    },
  },
);
```

**Сервер:** `chat_creation/index.ts`

- Валидация сессии
- Проверка что создатель — участник чата
- Генерация детерминированного chat ID (hash)
- Создание записи в таблице Chat

#### 5.2 Отправка сообщения

**Клиент:** `chat_page.dart`

```dart
// Строки 152-160
final res = await pageController.addMessage({
  'chatId': widget.chat['id'],
  'authorId': _user.id,
  'messageType': 'text',
  'delete': participantsMap,
  'message': {
    'text': messageMap,  // Зашифровано для каждого участника
  },
});
```

**Структура сообщения:**

```json
{
  "chatId": "abc123...",
  "authorId": "user1.near",
  "messageType": "text",
  "message": {
    "text": {
      "user1.near": "encrypted_for_user1...",
      "user2.near": "encrypted_for_user2..."
    }
  }
}
```

#### 5.3 Удаление сообщения/чата

Soft delete — помечает как удалённое, но не удаляет физически.

### Варианты замены

| Вариант | Описание | Сложность | Приватность |
|---------|----------|-----------|-------------|
| **NEAR Social DB** | Хранить сообщения on-chain | Высокая | Низкая (публично) |
| **IPFS + NEAR** | Сообщения в IPFS, хэши on-chain | Высокая | Высокая |
| **P2P (libp2p)** | Прямое соединение между клиентами | Очень высокая | Высокая |
| **Matrix Protocol** | Децентрализованный протокол чатов | Средняя | Высокая |
| **Отключить чаты** | Временно убрать функционал | Простая | - |

### Рекомендация

**Этап 1: Отключить чаты.** Самый простой путь для MVP децентрализации.

**Этап 2: IPFS + NEAR indexer.** Для полноценной децентрализации:

```
Архитектура IPFS + NEAR:

1. Сообщение шифруется на клиенте
            │
            ▼
2. Загружается в IPFS → получаем CID
            │
            ▼
3. CID записывается в SocialDB NEAR
            │
            ▼
4. Indexer отслеживает новые записи
            │
            ▼
5. Получатель загружает из IPFS по CID
```

## 6. Функция 5: Real-time стриминг

### Что делает

Supabase Realtime использует WebSocket для мгновенной доставки обновлений БД на клиент.

### Где используется

**Стриминг сообщений** — `chat_page.dart`:

```dart
// Строки 49-57
newMessageSubscription = Supabase.instance.client
    .from('Message')
    .stream(primaryKey: ['id'])
    .eq('chat_id', widget.chat['id'])
    .order('created_at', ascending: false)
    .listen(_handlePushNewMessage);
```

**Стриминг чатов** — `chat_list_body.dart`:

```dart
// Строки 35-37
chatSubscription = Supabase.instance.client
    .from('Chat')
    .stream(primaryKey: ['id'])
    .listen(_handleStreamData);
```

### Зачем нужно

1. **Мгновенные уведомления** — новые сообщения появляются сразу
2. **Синхронизация** — все устройства видят одинаковое состояние
3. **UX** — не нужно pull-to-refresh

### Варианты замены

| Вариант | Описание | Сложность |
|---------|----------|-----------|
| **Polling** | Периодические запросы к API | Простая |
| **NEAR Indexer WebSocket** | Подписка на события NEAR | Средняя |
| **P2P (WebRTC)** | Прямой обмен между клиентами | Высокая |
| **Push Notifications** | Серверные пуши (централизованно) | Средняя |

### Рекомендация

**Polling + NEAR Indexer.**

Для децентрализованного приложения:

1. **Polling** — простой fallback, опрос каждые N секунд
2. **NEAR Indexer WebSocket** — подписка на события в блокчейне

```dart
// Пример polling
Timer.periodic(Duration(seconds: 5), (_) async {
  final messages = await nearSocialApi.getMessages(chatId);
  _updateMessages(messages);
});
```

## 7. Варианты замены

### 7.1 Полное отключение чатов (Рекомендуется для MVP)

**Плюсы:**
- Минимум изменений
- Быстрая децентрализация основного функционала
- Можно вернуть позже

**Минусы:**
- Потеря функционала чатов

**Реализация:**
1. Скрыть UI чатов
2. Удалить Supabase зависимость
3. Оставить код для будущей миграции

### 7.2 NEAR Social DB для всего

**Плюсы:**
- Полная децентрализация
- Уже используется для постов
- Один источник данных

**Минусы:**
- Сообщения публичны (даже зашифрованные видны как данные)
- Стоимость транзакций
- Медленнее реального времени

**Реализация:**
```javascript
// Структура в SocialDB
{
  "user.near": {
    "chat": {
      "user2.near": {
        "messages": {
          "1706000000": {
            "encrypted": "base64_encrypted_message..."
          }
        }
      }
    }
  }
}
```

### 7.3 IPFS + NEAR Indexer

**Плюсы:**
- Приватность (данные в IPFS)
- Децентрализованное хранение
- Масштабируемость

**Минусы:**
- Сложная архитектура
- Нужен indexer
- IPFS garbage collection

### 7.4 Matrix Protocol

**Плюсы:**
- Готовый децентрализованный протокол
- E2E encryption из коробки
- Федерация серверов

**Минусы:**
- Нужен Matrix homeserver
- Интеграция с NEAR auth

## 10. Заключение

### Критические зависимости от Supabase

| Функция | Критичность | Замена возможна |
|---------|-------------|-----------------|
| Auth (UUID) | Низкая | Да, локально |
| Верификация подписи | Средняя | Да, на клиенте |
| Хранение ключей | Высокая | Да, SocialDB |
| Чаты/сообщения | Высокая | Да, но сложно |
| Real-time | Средняя | Да, polling |

### Рекомендуемый путь

**Для быстрой децентрализации:** Отключить чаты, удалить Supabase.

**Для полной децентрализации:** NEAR SocialDB для ключей + IPFS для сообщений.
